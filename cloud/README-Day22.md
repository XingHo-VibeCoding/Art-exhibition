## 〇、先理解：今天比 Day 18 多了两样东西

云函数要在公网上被敲到，永远需要**两样东西同时到位**（与 Day 18 相同）：

| # | 是什么                       | 类比    | 本项目的值       |
| - | ------------------------- | ----- | ----------- |
| ① | **函数本体**（代码跑在云端）          | 屋子里的人 | 函数名 `note`  |
| ② | **HTTP 访问路径**（把 URL 指向函数） | 门牌号   | `/api/note` |

> ⚠️ **新函数不共享旧函数的环境变量** —— `works` / `like` 上那把数据库钥匙，  
> `note` 上要**再配一次**。这是最容易漏的一步，也是「函数明明传上去了、一调就报未配置密钥」的唯一原因。

**今天是新的两样：**

1. **一条路径吃四个方法**。以前 `like` 只认 `POST`，`works` 只认 `GET`；  
   今天 `/api/note` 要同时认 `GET` / `POST` / `PATCH` / `DELETE`，靠方法分派。
2. ★ **`PATCH` / `DELETE` 要带 `:id`** —— 而「平台会不会把 `/api/note/xxx` 的**末段**转发进函数」，  
   **我们没有证据**（线上现有三个函数都只有一级路径）。  
   所以函数里做了**三处兜底**（路径末段 → query → body），  
   并且本手册**专门留了第 6 步**去实测这一点。**不赌平台行为。**

### 第 4 步 · 确认 CORS 覆盖了新路径

Day 20 配的 CORS 是**精确白名单**（真域名才回 `access-control-allow-origin`，不是 `*`），  
已验收的事实是「`OPTIONS /api/like` → 204 + `allow-methods: POST`」。

**要确认的一件事**：这份白名单是**整个访问服务共用**，还是**按路径分别配**？

- 若是共用 → 新路径 `/api/note` **自动继承**，无需操作
- 若是按路径 → 需要为 `/api/note` **单独加一条**，且 `allow-methods` 要含  
  **`GET / POST / PATCH / DELETE`**（⚠️ 少了 `PATCH` 或 `DELETE`，浏览器预检会被拦下）

**怎么判断**：配完第 3 步后跑一次探针（第 6 步里带 `Origin` 的那两条），  
看响应头里有没有 `access-control-allow-origin`。有 → 共用，收工；没有 → 回此处补配。

> 为什么今天特别要盯 CORS：检查台 `checkup.html` 上的「删除」按钮是**浏览器发起**的跨域请求，  
> 且 `DELETE` 属于**非简单请求**，一定会先发 `OPTIONS` 预检。预检不通过 = 页面上删不掉，但接口本身是好的 ——  
> 这种「接口没错、页面报错」最难查，所以提前堵住。

### 三个悬念全部解开（都有证据）

| 悬念 | 结论 | 证据 |

> `-1499147979`），于是全判「无 CORS 头」——**是我自己制造的假阴性**，差点让你白跑一趟控制台。

### 修掉两个「部署后才暴露」的问题（已改代码 → 需重传）

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `GET /api/note?workId=…` 回 **200，但 `notes: []`**（`total` 却是对的，2 → 3 → 2 一路正确） | 数据访问层 `listByWork` 回的是 `{ok, data}`（通道原始形状），入口层按两层约定读的是 `rows` —— **两边对不上**。`total` 走的是另一条查询（`countByWork`）所以是对的，形成「数量对、列表空」这种极具欺骗性的长相 | 在 `notesRepository.listByWork` 就地把结果**归一化**成 `{ok:true, rows}`，与 `findById` 的 `row`、`countByWork` 的 `count` 同族 |
