## 〇、先理解：部署为什么要分两半

一个云函数要在公网上被敲到，需要**两样东西同时到位**：

| # | 是什么 | 类比 | 本项目的值 |
|---|---|---|---|
| ① | **函数本体**（代码跑在云端） | 屋子里的人 | 函数名 `like` |
| ② | **HTTP 访问路径**（把 URL 指向函数） | 门牌号 | `/api/like` |

Day 17 只配了①就会 404，只配了②就会没人应答。**两个都齐了，才算"这扇门开了"。**

> ⚠️ **新函数不会共享旧函数的环境变量** —— `works` 上那把数据库钥匙，`like` 上要**再配一次**。
> 这是今天最容易漏的一步，也是"函数明明传上去了，一调就报未配置密钥"的唯一原因。

### 第 2 步 · 配环境变量（★ 今天最容易漏的一步）

| 项 | 内容 |
|---|---|
| 位置 | 控制台 → 云函数 → **`like`** → 「函数配置」→ **环境变量** → 新增 |
| 变量名 | **`CLOUDBASE_API_KEY`**（一字不差，代码里就是按这个名字读的） |
| 变量值 | 数据库那把 API Key（**与 `works` 函数用的是同一把**） |
| 生效时机 | **改完下次调用即生效，不需要重新部署** |

**钥匙从哪来？**
1. **先看 `works` 函数的环境变量** —— 如果控制台能显示明文，直接复制过来即可
2. 如果显示为遮蔽（`****`）拿不到值 → 去 **左下角「环境管理」→「API Key 配置」→ 下半区「服务端 API Key」→ 创建** 一把新的
   - 单个环境最多 5 把，**新建不影响旧的**，旧的继续有效
   - ⚠️ 明文**只在创建那一刻显示一次**，务必当场复制保存
   - ⚠️ 上半区是「客户端 Publishable Key」（`anon` 角色），**别拿错**
3. 历史上 Day 17 配置成功后，函数自检报出过 **Key 长度 = 932**（可用来核对是否拿错）

**做完该看到什么**：`like` 的环境变量列表里有一条 `CLOUDBASE_API_KEY`。

**容易踩的坑**
- ❌ 名字打错（如 `CLOUDBASE_APIKEY`、`CLOUDBASE_API_KEY ` 带空格）→ 函数会报「服务端未配置数据库密钥」，这是**指定中文提示**，看到它就说明名字错了
- ❌ 拿成了上半区的 `anon` 客户端 Key → 会报权限不足
- ❌ 把 Key 复制进代码文件 / 提交到仓库 → **绝对禁止**（本手册只让你填在控制台里）

**现象**：跑完 ①②③④ 之后去查库，`likes` 表**仍是 8 行**，作业要的"数据库新增的那一行"**不在表里**。

| 时点 | 动作 | `theology-01-0x0` 赞数 | 表行数 |
|---|---|---|---|
| 基线 | — | 3 | 8 |
| 命令① | INSERT | 4 | 9 |
| 命令② | **DELETE** | 3 | **8** ← 坑在这里 |

**对策**：`_ref/day18-finalize.sh` —— 对同一 `workId + visitorId` 再发一次 = 第 3 次 toggle，
从"取消态"回到"已赞态"，表回到 9 行。**该脚本带暂停点，且结尾明确警告"不要再跑第 2 遍"。**

> **沉淀**：toggle 类接口，「写入前 / 写入后」的对比截图**必须在数据还活着的时候截**。

## 八、一处旁证：SQL 编辑器里的 `UPDATE` 语句

主人现场截图里有一句 `UPDATE "works" SET "name" = 'LOVE / SIGNAL' WHERE "order" = 85;`。

**核查结论：无实际影响。** `db/seed.sql:150` 里 `studies-09-0x0` 的名字**本来就是** `'LOVE / SIGNAL'`
（`mvp/index.html:1692` 同值），所以那是一次**幂等操作**（把值改成它已有的值）。

**但要点出来**：SQL 编辑器的"执行"很容易**一次跑完整个标签页的所有语句**。
若里面夹着 `UPDATE` / `DELETE`，就会**绕过接口直接改数据**。
→ 纪律：**做查询时选中单条再执行**；改数据优先走接口（Day 19 之后），确需直改则先备份、后核对。
