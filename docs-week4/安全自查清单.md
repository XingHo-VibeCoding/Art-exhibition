## 一、A 组 · 密钥与配置（**红线，最先做**）

> 这组的特殊性：**任何一项不通过，今天不许做别的事，先处理它。**

### A1 · 当前仓库里没有真实密钥

**复制执行**（在仓库根目录）：

```bash
git grep -n -I -i -E "password|passwd|secret|sk-[A-Za-z0-9]{6,}|postgres(ql)?://|api[_-]?key|credential|private[_-]?key|BEGIN RSA|ACCESSTOKEN" -- .
```

**通过判据**：会命中一些行（这是正常的），但**逐条看完后，没有一处是真实值**。

怎么分辨「变量名」和「真实值」——

| 命中长这样 | 判定 |
|---|---|
| `const KEY = process.env.CLOUDBASE_API_KEY;` | ✅ 变量名，过 |
| `README` 里写「把 API Key 配到环境变量」 | ✅ 文档说明，过 |
| `apiKey = "eyJhbGciOi..."`（一长串无意义字符） | ❌ **真实值，不过** |
| `postgres://user:pass@host:5432/db` | ❌ **真实值，不过** |

**补充一把更严的筛子**（专门抓「没有特征词、但形状像密钥」的长串）：

```bash
git grep -n -I -E "[A-Za-z0-9_\-]{40,}" -- .
```

**通过判据**：命中的全是**注释分隔线**（一排 `-` 或 `=`）或**环境 ID**，没有随机长串。

### A2 · Git 全部历史里没有密钥

> ★ 为什么必须单查历史：**文件里删掉了，历史里还在**。public 仓库的历史全世界都能翻。

```bash
git log --all --oneline -S "postgres://"
git log --all --oneline -S "sk-"
git log --all --oneline -G "Bearer [A-Za-z0-9_\-]{20,}"
git log --all --oneline -i -S "password"
```

**通过判据**：四条全部 **0 命中**。

⚠️ **命中了不要直接判死**。`sk-` 这种短特征词会被无辜单词撞上（比如 CSS 的 `mask-image`、PNG 二进制里的字节巧合）。
命中后必须**看上下文**再结论：

```bash
git grep -n -i -E ".{0,25}sk-.{0,25}" <提交号> -- .
```

判据不变：上下文里是**英文单词或乱码**，就是误报；是**一长串随机字符**，才是真泄漏。

### A3 · `.env` 进不了仓库

```bash
git check-ignore -v .env
```

**通过判据**：原样输出一行，形如 `.gitignore:5:.env`。
**没有任何输出 = 没被忽略，不合格**，要修 `.gitignore`。

再确认根目录**根本不存在** `.env` 实体文件：

```bash
ls -a | grep -E "^\.env"
```

**通过判据**（二选一，任一种都算过）：

- **输出为空** —— 根目录一个 `.env*` 都没有（**本仓库当前就是这种**，因为模板建在 `cloud/` 下）
- 只出现 `.env.example` —— 有模板但没真身

**不合格的样子**：输出里出现光秃秃的 `.env`（没有 `.example` 后缀的那个）。

### A4 · `.env.example` 存在，且里面没有真实值

```bash
ls cloud/.env.example
grep -n -i -E "password|secret|sk-[A-Za-z0-9]{6,}|postgres://|Bearer [A-Za-z0-9]{10,}|[A-Za-z0-9_-]{40,}" cloud/.env.example
```

**通过判据**：第一条能列出文件；第二条 **0 行输出**（模板里只有字段名，等号右边全是空值或占位说明）。

再确认模板**自己没被 gitignore 误吞**（这份模板要是提交不上去，等于白建）：

```bash
git check-ignore -v cloud/.env.example
```

**通过判据**：**无输出**（exit=1）= 没被忽略，提交得进去。
若输出了忽略规则 = 模板永远进不了仓库，不合格。

### A5 · 真实值只存在于云函数控制台

**操作方法**（图形界面，无法用命令验证，必须亲眼看）：

1. 进 CloudBase 控制台 → 云函数 → 函数列表
2. 逐个点开 `works` / `like` / `note` → 「函数配置」→「环境变量」
3. 确认 `CLOUDBASE_API_KEY` 有值

**通过判据**：**三个函数各有自己的一份**。

> ⚠️ 最容易漏的一条：**CloudBase 的云函数之间不共享环境变量**。
> 只配 `works`，`like` 和 `note` 就会报「缺少凭据」——Day 18 和 Day 22 都栽在这里。
> 判据必须是「三个函数逐一确认」，不是「配过了」。

## 二、B 组 · 三类错误都返回中文提示

> 这一组的判据只有一句话：**用户看到的每一个字都得是中文，而且得告诉他下一步能做什么。**

### B1 · 用户输入错 → `400`

```bash
curl -s -X POST "https://art-exhibition-d7ggtul83d566a6c9.service.tcloudbase.com/api/like" \
  -H "Content-Type: application/json" -d "{}"
```

**通过判据**：HTTP **400**，`error.message` 是**中文**，形如「缺少必填参数 workId」。

「告诉用户改什么」才算人话 —— 反例是「参数错误」（说了等于没说）。

### B2 · 网络 / 接口错 → `503`

**线上实测（需要你亲手断网，我断不了你的网）**：

1. 打开 `checkup.html`
2. 断开网络
3. 点任意按钮触发请求

**通过判据**：页面出现「**网络好像断开了，请检查网络连接后再试一次**」。
**不合格的样子**：「网络请求失败：**Failed to fetch**」——后半截是浏览器英文，谁也读不懂。

**后端分流自证**（不用断网，本地跑）：

```bash
node _ref/day23-error-tests/three-classes-test.js
```

**通过判据**：输出 `50 PASS / 0 FAIL`，且其中包含这两条**逆命题**：

```
④★ 逆命题 NETWORK 不得回 500   PASS
⑤★ 逆命题 DB 不得回 503        PASS
```

> ★ 为什么必须有「逆命题」：只断言「网络错应回 503」，就算代码压根没改、期望值本身写错了，也可能 PASS。
> 两条方向相反的断言同时成立，503 和 500 才是真的两条道。**这是「全绿但没验证到点上」的解药**（Day 22 栽过一次）。

### B3 · 服务端错 → `500` + 中文，且**不漏堆栈**

**线上实测**（临时把 `works` 函数里查询的表名改成一个不存在的名字，重传 zip，触发一次，然后**务必改回来**）。

**通过判据** —— 三条同时成立：

| # | 判据 |
|---|---|
| 1 | HTTP **500**，`error.code` 为 `INTERNAL_ERROR` |
| 2 | `error.message` 是**纯中文**（形如「服务端处理请求时出错，请稍后再试」） |
| 3 | 响应体里**搜不到** `stack` / `select` / `at ` 等任何技术细节 |

**自证命令**（离线，替代线上破坏性实测）：

```bash
node _ref/day23-error-tests/three-classes-test.js 2>&1 | grep -E "不漏|逆命题"
```

> 注意一个容易误判的点：跑脚本时屏幕上**会**刷出 `at handleRequest (...)` 这类堆栈行。
> **那不是 bug，是证据** —— 堆栈被打进了服务端日志（控制台可见，给排查用），
> 而响应体里的 `message` 仍是纯中文（给人看的）。**日志要详细，响应要人话**，两者不矛盾。

### B4 · 前端没有裸报错

```bash
node _ref/day23-error-tests/frontend-message-test.js
```

**通过判据**：`17 PASS / 0 FAIL`。

> ★ 一个判定边界，写在这里免得你跟我一样纠结：
> 「接口地址不存在（HTTP 404），可能是路径还没配好」里**含英文数字 `HTTP 404`**，
> 但它是**中文起头**、状态码放括号里当备注 —— 用户看得懂、也知道下一步查什么，**不算裸报错**。
> 「裸报错」的判据是**起头的那个词是不是中文**，不是「含不含英文字符」。

## 三、C 组 · 输入边界

> 一组的共同判据：**非法输入必须被挡在门口，返回 400 中文；绝不能带着脏数据进数据库。**

| # | 测什么 | 怎么触发 | 通过判据 |
|---|---|---|---|
| **C1** | 空值 | `POST /api/like` body 为 `{}` | 400「缺少必填参数 workId」 |
| **C2** | 超长 | `workId` 填 100 个字符 | 400（契约上限 64 字符） |
| **C3** | 类型错 | `workId` 填数字 `123` 而非字符串 | 400，提示要字符串 |
| **C4** | **SQL 注入** | `workId` 填 `'; DROP TABLE works;--` | **404 `NOT_FOUND`** |

**C2 / C3 的触发命令**（C1 同 B1）：

```bash
curl -s -X POST "https://art-exhibition-d7ggtul83d566a6c9.service.tcloudbase.com/api/like" \
  -H "Content-Type: application/json" \
  -d '{"workId":123,"visitorId":"test"}'
```

**C4 为什么要单独列，以及为什么「404」才是对的**：

本项目的数据库访问走 **Data API（PostgREST）**，查询参数是**结构化字段**（`workId=eq.xxx`），
**不是字符串拼接的 SQL**。所以那句注入语句会被老老实实当成「一个普通的作品编号」去查，
查不到 → **404**。

判读：

| 实际返回 | 结论 |
|---|---|
| **404 NOT_FOUND** | ✅ 正确 —— 说明它只是个查不到的普通字符串，没被当 SQL 执行 |
| 500 | ❌ 可疑 —— 语句可能被拼接进了查询 |
| 表真的没了 | ❌ 严重事故 → 立刻走 §四 |

C4 测完请确认 `works` 表**仍在且行数仍为 85**（`GET /api/works` 的 `count` 应为 85）。

## 四、★ 发现真实密钥时的应急流程

**顺序不可颠倒。前三步是「止损」，后两步才是「清理」。**

| 步 | 动作 | 为什么必须这一步 |
|---|---|---|
| **1** | 到对应平台控制台**立即作废**该密钥 | 密钥一旦进过 public 仓库，就应视为**已公开**。改代码救不了一个已经泄出去的密钥 |
| **2** | **重新生成**新密钥 | 作废不等于有替代品，服务会中断 |
| **3** | 把新值**配进**云函数控制台的环境变量（三个函数各一次） | 服务恢复 |
| 4 | 代码里改用环境变量引用 | 防止再次硬编码 |
| 5 | 清理 Git 历史 | 减小扩散面 |

> ⚠️ **只改代码、或只清理历史，都不算处理完。**
> 密钥的生命周期在**平台侧**，不在仓库里。仓库清得再干净，那个密钥在平台上仍然有效。
