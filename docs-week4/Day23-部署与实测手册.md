## 第 4 步 · 三类错误实测（三张截图，今天的作业）

打开公网上的 `checkup.html`（记得先点「确定访问」），然后依次做：

### 📷 截图 1 · 用户输入错

| 项 | 内容 |
|---|---|
| 怎么做 | 在检查台上**提交一个空的 / 格式不对**的输入（比如点赞但不填作品编号） |
| 该看到 | HTTP **400** + 中文提示，形如「**缺少必填参数 workId**」 |
| 不合格 | 出现英文堆栈，或提示是「参数错误」这种说了等于没说的 |

### 📷 截图 2 · 网络错（**必须你亲手断网**）

| 项 | 内容 |
|---|---|
| 怎么做 | 断开网络 → 在页面上触发任意请求 |
| 该看到 | 「**网络好像断开了，请检查网络连接后再试一次**」 |
| 不合格 | 「网络请求失败：**Failed to fetch**」——出现这句就说明改动没生效（多半是 `checkup.html` 没传上去） |

### 📷 截图 3 · 服务端错

这里给你**两条路，选一条**：

**路线甲（推荐，30 秒，不用重传代码）**

1. 控制台 → 云函数 `works` → 函数配置 → 环境变量
2. 把 `CLOUDBASE_API_KEY` 的值**临时改成一个错的**（比如末尾加个 `x`）
3. 触发一次请求 → 应看到 HTTP **500** + 中文提示
4. **改回正确值**（改完下次调用即生效，不用重部署）

**路线乙（严格，要重传）**

把 `works` 函数里查询的表名改成不存在的名字，重新打包上传，触发一次，**然后务必改回来**。

**通过的判据**（三条同时成立）：

- [ ] HTTP **500**，`error.code` 是 `INTERNAL_ERROR`
- [ ] `error.message` 是**纯中文**
- [ ] 响应体里**搜不到** `stack` / `select` / `at ` 这类技术细节

> ★ 一个容易误判的点：控制台日志里**会**出现 `at handleRequest (...)` 这种堆栈。
> **那是设计意图，不是 bug** —— 堆栈进日志（给排查用），响应只给人话（给用户看）。

## 第 5 步 · 密钥搜索截图（作业的另外一张）

在仓库根目录跑这一条，然后截图：

```bash
git grep -n -I -i -E "password|passwd|secret|sk-[A-Za-z0-9]{6,}|postgres(ql)?://|api[_-]?key|credential|private[_-]?key|BEGIN RSA|ACCESSTOKEN" -- .
```

**会命中 41 行，全是变量名**（形如 `process.env.CLOUDBASE_API_KEY`）——这是正常的，不是泄漏。

### 拿到「0 命中」的那条命令（作业要的）

```bash
git grep -n -I -E "[A-Za-z0-9_\-]{40,}" -- . | grep -vE "\-{40,}|https?://|tcloudbase"
```

**输出 0 行。** 这条抓的是「40 位以上的连续串」——**真密钥的形状**。

### 建议三张连着截，逐层看它怎么归零

```bash
git grep -n -I -E "[A-Za-z0-9_\-]{40,}" -- . | wc -l
# → 39   原始命中

git grep -n -I -E "[A-Za-z0-9_\-]{40,}" -- . | grep -vE "\-{40,}" | wc -l
# → 4    去掉注释分隔线后（剩的全是公网 URL 里的域名随机串）

git grep -n -I -E "[A-Za-z0-9_\-]{40,}" -- . | grep -vE "\-{40,}|https?://|tcloudbase" | wc -l
# → 0    ★ 最终结果
```

> ⚠️ **为什么第二步会剩 4 行**：CloudBase 的公网域名自带随机段
> （`art-exhibition-d7ggtul83d566a6c9-1499147979.tcloudbaseapp.com`），长度过了 40 位，
> 形状上跟密钥很像 —— **这是域名，不是密钥**。
>
> 这一条我第一次写手册时漏了，命令实际输出 4 行、不是 0 行，**实测后才发现的**。
> 写在这里的意思是：**过滤掉的到底是什么，你得能说清楚** —— 否则「0 命中」这个结论站不住。
