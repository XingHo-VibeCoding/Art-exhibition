# Day 24 · 核心流程测试清单（感想 note 全链路）

> **性质**：这一天唯一的**找 Bug 工具**。先有清单，才有 Bug。
> **纪律**：期望值**一律来自 `api-contract.md`**（每条后面标了 § 出处）。不许凭"我觉得应该是"写期望 ——
> 期望写错的话，测出来不是「通过」就是「假失败」，两种都是白跑。
> **判据要求**：每条必须给出**可机器判断**的判据（状态码 / 字段值 / 数量），不许出现「看起来正常」这类判词。

### 三轮执行的意义

| 轮次 | 在什么时候跑 | 产出 |
|---|---|---|
| **第 1 轮** | 修复**前** | `_ref/day24-evidence/before-01.md` —— 基线，用来挑 Bug |
| **第 2 轮** | 修复**后** | `after-01.md` —— 与 before 逐行对照，确认「除已修项外全部一致」 |
| **第 3 轮** | 第 2 轮有疑问时 | 排除偶发（偶现 Bug 最会骗人） |

> ★ 判定 Bug 优先级的标准只有一条：**它对「选中 Trojan 的核心链路」的破坏程度**。
> 主链路 = 打开检查台 → 读列表 → 写感想 → 刷新确认 → 改 → 删。

## C · 增 · `POST /api/note`（C1–C9）

> 每次新增前先清掉靶作品上的遗留，保证不撞 409。

| # | 操作 | 期望（契约依据） | 判据 |
|---|---|---|---|
| C1 | 正常新增 `{workId, visitorId, text}` | 200，回吐 `note._id`，§4.4 | `status===200` 且 `typeof data.data.note._id==='string'` 且非空 |
| C2 | **刷新确认**：立刻 `GET` 一次 | 新增那条**出现在列表里**，`total+1` | 新 `_id` ∈ `notes[]._id`；`total` 比增前 **+1** |
| C3 | 回吐的 `note` 形状 | §4.4 | keys 严格 = `_id/workId/text/createdAt`（**不含 visitorId**） |
| C4 | `text` 缺 | **400** `INVALID_PARAM`，§4.4 | `status===400` |

## D · 改 · `PATCH /api/note/:id`（D1–D8）

| # | 操作 | 期望（契约依据） | 判据 |
|---|---|---|---|
| D1 | 三种取 id 姿势都通：路径末段 / `?id=` / body `id` | 三处都取得到，§4.6 | 三种调用均返回 **200**（用同一条记录测） |
