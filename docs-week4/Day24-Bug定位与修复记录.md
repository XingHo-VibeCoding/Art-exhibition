## 二、定位：候选原因排序 → 逐条证伪

### 四个候选

| 序 | 候选原因 | 给它排这个位置的理由 |
|---|---|---|
| **H1** | **键盘入口不检查 `addBtn.disabled`** | 页面把 Enter 直接绑到了 `<input>` 上，那个处理器是**自己**调 `addNote()` 的，从不看按钮状态。最贴合现象 |
| H2 | `addBtn` 上重复绑了多次 click 监听 | 若有，点一次就会发 ≥2 个请求；须排除，否则会误判成"绑定泄漏" |
| H3 | 页面有 `<form>`，回车触发了原生提交 | 经典成因，必须先排掉 |
| H4 | `fetch` 自动重试造成重复 | 若成立，请求之间会有重试间隔；不该是毫秒级连发 |

### 验证方法与实际结果（`root-cause.js`）

| 变体 | 操作 | 实测 POST 数 | 它证伪了谁 |
|---|---|---|---|
| **A** | 只点鼠标 **3 次**（不碰键盘） | **1** | ✅ 排除 H2（3 次点击只出 1 个请求 = 没有重复绑定）；同时证明**禁用态对鼠标完全生效** |
| **B** | 只按回车 **3 次**（不碰鼠标） | **3**，首尾相隔 **0 ms** | ✅ 排除 H4（0ms = 连发，不是重试）；✅ **H1 成立** —— 不点按钮也照样发请求 |
| **C** | 点 1 次 + 回车 2 次（Bug 现场） | **3** | 印证：鼠标的 1 + 键盘的 2 = 3 |
| — | 读 DOM：`document.querySelectorAll('form').length` | **0**，输入框不隶属于任何 form | ✅ 排除 H3 |

### ★ 锁定根因

> **`addBtn.disabled` 是浏览器替按钮做的事，它只管得住鼠标。**
> `<input>` 上的 `keydown` 处理器是页面自己调 `addNote()` 的，它从来不读按钮的那个属性。
> 于是「提交」这一个用户动作有了**两条互不相同的准入路径**，而闸门只堵了其中一条。

**这条对照实验是该Bug唯一的定位线索** —— A 组证明"鼠标 3 次只发 1 个"这件事，同时就把 H2（重复绑定）彻底否掉了；
如果没有 A 组，看到"3 次请求"很容易一路走岔到"按钮绑定了三遍"上去。

## 三、修复

**文件**：`checkup.html`（面板 04 的 `addNote()`）

**改法**：把闸门从**按钮的属性**上，挪到**这段流程本身**。

```diff
+ var addBusy = false;
  async function addNote(){
+   /* 闸门：任何一个入口都从这里过 */
+   if (addBusy) return;
    ...
-   addBtn.disabled = true;
+   addBusy = true;
+   addBtn.disabled = true;
    sayRun('POST /api/note …');
-   var r = await postJSON(...);
-   ... 整段 if/else ...
-   addBtn.disabled = false;
+   try {
+     var r = await postJSON(...);
+     ... 整段 if/else（原样不动）...
+   } finally {
+     addBusy = false;
+     addBtn.disabled = false;
+   }
  }
```

**两个刻意的取舍**

1. **`addBtn.disabled` 保留**。它现在是"给人看的"（变灰 = 正在处理），不再是"管事的"。视觉反馈要留，**但别再把安全寄存在它身上**。
2. **复位放在 `finally` 里**。若哪天 postJSON 抛了异常，写在末尾的复位会被跳过，按钮就此永久锁死 —— 那比多发出几个请求糟得多。

> 今天**没有**给 `commitEdit()`（保存）加同样的闸门 —— 那是同一个病灶的第二个 Bug，已登记为 BUG-02，**今日按规矩不修**。

## 八、每日一问

> **你是怎么排除掉其他原因、锁定真正原因的？**

**答：靠一组「对照组」，而不是靠"看起来像"。**

我没有直接去看代码猜答案，而是先列了四个候选，然后给每一个**设计一条能证伪它的实验**：

| 我想否掉的假设 | 用来否掉它的实验 | 结果 |
|---|---|---|
| 是不是按钮绑了三遍？ | 只点鼠标 3 次，数发出几个请求 | 只有 **1 个** → 否掉 |
| 是不是表单在提交？ | 数页面上有几个 `<form>` | **0 个** → 否掉 |
| 是不是网络在自动重试？ | 量前后两个请求差多少毫秒 | **0 ms** → 否掉 |
| —— | 最后：完全不碰鼠标，只敲回车 | **照样发请求** → 只剩这一个解释 |

真正的转折点是第一组：**"鼠标连点 3 次只发出 1 个请求"**。
它一举证明了两件事 —— 既没有重复绑定，又说明禁用按钮这件事**本身是好的**。
剩下的可能性就只剩一条：毛病不在"按钮"，而在"另一条没人管的门"。

一句话总结这个方法：**不是找到支持答案的证据，而是把其他答案一个个杀死，看最后站着的是谁。**
