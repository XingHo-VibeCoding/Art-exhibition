## 0. 演练设计（怎么算「真做」）

真实事故的时序是：**新版上线 → 发现问题 → 决定回滚 → 执行 → 恢复**。
本次演练按同一时序复刻，只改 1 个文件、不碰任何数据：

| 角色 | 谁 |
|---|---|
| 「新版」 | 我生成的 v1.1 坏版本（`_ref/day26-drill/v1.1-broken/index.html`，仅加一条红色横幅） |
| 「上一稳定版」 | v1.0（`_ref/rollback/v1.0/index.html`，142760B，线上逐字节副本） |
| 上传操作 | 主人（本机无 cloudbase/tcb CLI，静态托管只能控制台手动上传） |
| 复核与计时 | AI（公网侧独立复核，不信截图只看字节） |

**计时口径**：`T0` = 公网侧确认「坏版本已生效、决定回滚」的时刻（不含上传坏版本的时间——真实事故里也是「先发现、再决定」才起算）。
`T2` = 公网侧确认「v1.0 已恢复可用」的时刻。**总耗时 = T2 − T0**。

## 5. 复盘与教训

### 5.1 演练暴露的真问题（值钱的部分）

**① 静态托管「没有一键回滚」是本次预备阶段最大的发现。**
官方控制台只提供「文件管理」+「同名上传=覆盖」，**没有历史版本列表、没有回滚按钮**。所以本项目的「静态托管回退」实操真身 = **用上一版文件重新上传覆盖**。
→ 由此推出**一条必须提前做的准备**：**平时就要把「当前线上文件」存一份权威副本**（本次存在 `_ref/rollback/v1.0/`）。出事那一刻才去想办法取文件，就已经晚了。

**② `core.autocrlf=true` 让「从 git 取回上一版」成为陷阱（本次实测踩到）。**
`git show v1.0:mvp/index.html` 得到 **140280B**，而线上是 **142760B**（混合行尾）。git 的行尾归一化**有损**，无法逐字节重建线上文件。
→ **权威回退来源 = 线上文件本身**（下载 + 自校验），git 标签仅供源码对照、**不可直接上传**。已写进回滚手册 §0。

**③ 演练本身很"轻"，但它证明的是一条链。**
真正的耗时不在「点上传」，而在**CDN 缓存刷新 + 确认生效**（约 1–2 分钟）。这意味着真实事故中，**即使你 10 秒内点完上传，用户仍要看一段时间坏页面** → 引出下面这条改进方向。

### 5.2 改进方向（不今天做，登记）

| 项 | 说明 |
|---|---|
| 绑自定义域名 | 根治默认域名的「站外导航提示页」问题，也让 CDN 行为可控（第 4 周优先项） |
| 把线上文件副本纳入例行 | 每次发布后立刻 `curl` 存一份 + 记 sha256，作为「回退弹药」 |
| 演练频率 | 建议每次正式发布（打 tag）后顺手跑一次 1 分钟版演练 |

### 5.3 自评：敢不敢用？

**敢。** 理由不是「感觉没问题」，而是三个可复核的事实：判据是**字节级**的（不靠肉眼）、恢复是**逐字节验证过**的（不是"看起来对了"）、检查台**复跑全绿**（除了那个诚实的 D2）。
唯一要补的是**速度**：2 分半里有一大半是 CDN 刷新，这部分靠流程拿不回来——只能靠「备好副本 + 缩短发现时间」。
