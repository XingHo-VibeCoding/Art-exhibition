## 〇、三条铁律（先读这三条，再读步骤）

### 铁律 1 · 回滚只治代码，不治数据

| 事故类型 | 回滚能救吗 | 靠什么救 |
|---|---|---|
| 页面白屏 / 样式崩坏 / JS 报错 | ✅ 能 | 退回上一版部署 |
| 接口 500 / 云函数逻辑改坏 | ✅ 能 | 重新部署上一版云函数 |
| **数据被误删 / 被改错** | ❌ **不能** | **只能**用发布前导出的备份重新导入 |
| 数据表结构被改坏 | ❌ 不能 | 靠备份 + 迁移 SQL 回修 |

> ⚠️ **退回上一版部署不会让数据回到上一版。** 「代码回退」与「数据恢复」是两条独立的路，
> 必须**分开练、分开用**。本手册把它们分成第 3 章与第 5 章，中间隔着一整个第 4 章 —— 这不是排版偶然。

### 铁律 2 · 本项目的「静态托管回退」= 用上一版文件重新上传覆盖

**云开发静态网站托管控制台没有「一键回滚到上一版」按钮。**
官方文档只提供两个入口：
- 「文件管理」—— 浏览 / 上传 / 删除托管文件
- 上传一个**已存在**的文件 → **行为 = 覆盖**（原文：「表现与上传不存在的文件完全一样」）

→ 所以「退回上一版」在**本项目**的真身是：

> **拿出上一版的产物文件 → 重新上传 → 覆盖掉出问题的版本。**

**「上一版」放在哪？**（三层来源，**按权威性排序**；⚠️ 顺序与直觉相反，见下方陷阱）

| 优先级 | 来源 | 怎么取 | 可靠性 |
|---|---|---|---|
| ① | **线上文件本身** | 带站内 Referer `curl -o` 下载 `/` | ★★★ 最权威（就是访客看到的那份字节） |
| ② | **本地工作区文件** | `cp mvp/index.html <目标>` | ★★ 前提：已核对与线上字节数相等 |
| ③ | git 标签 / 提交 | `git show v1.0:mvp/index.html` | ⚠ **仅源码级对照，不可直接上传** —— 见下 |

> ### ★ 常温储备规则（本次演练推出，务必执行）
> 因为控制台**没有历史版本**，所以「回退弹药」只能靠**平时存**：
> **每次发布/上传之后，立刻从线上 `curl` 下载一份当前文件，存进 `_ref/rollback/<版本>/index.html` 并记下 sha256。**
> 出事那一刻再去想办法取文件 = 已经晚了。（本次演练用的 `_ref/rollback/v1.0/index.html` 就是这么来的。）

> ### ⚠️ 陷阱：`git show` 取回的版本 ≠ 线上版本（2026-10-12 实测）
>
> 本仓库 `core.autocrlf=true`：**git 里存 LF，工作区检出 CRLF**。
> 实测三个数字：
>
> | 对象 | 字节数 | 说明 |
> |---|---|---|
> | `git show v1.0:mvp/index.html` | **140280** | 全 LF（0 个 CRLF） |
> | 工作区 / 线上 `mvp/index.html` | **142760** | **混合行尾**：2480 个 CRLF + 302 个孤立 LF |
> | 若强行把 LF 全转 CRLF | **143062** | 2782 个 CRLF —— 仍然 ≠ 142760 |
>
> **原因**：git 的行尾归一化**有损** —— 它能 CRLF→LF，却记不住「哪些 LF 本来没有 `\r`」。
> → **从 git 仓库无法逐字节重建线上文件。**
> → 若拿 `git show` 的产物和线上比对，会得出「标签里的版本 ≠ 线上版本」的**错误结论**。
>
> **教训（可迁移）**：**比对两个版本前，先统一「比较口径」**（这里就是行尾符）。
> 否则「不一致」这个结论本身可能是假的 —— 和「裸 curl 测静态托管得假 PASS」是同一类错误的两面。

### 铁律 3 · 每次回滚必须留下时间戳

没有数字的记录 = 只写了方法，没真做。**至少记三个**：
`T0 发现问题` → `T1 覆盖上传完成` → `T2 公网确认恢复`。**总耗时 = T2 − T0。**

## 一、触发条件：什么情况必须回滚（判断表）

> 这张表的作用是**在慌的时候替你思考**。事故现场最怕的不是不会操作，是**不知道该不该动手**。

### 1.1 分级表

| 级别 | 现象 | 动作 | 时限 |
|---|---|---|---|
| **P0 · 立即回滚** | 首页打不开 / 白屏 / 全站 404；主接口大面积 500；**数据被误删或改错** | 立刻回滚，**不评估、不尝试现场修** | 分钟级 |
| **P1 · 尽快回滚** | 部分功能不可用（点赞/感想面板报错）；样式明显崩坏但页面能开；错误信息里泄漏堆栈或英文原文 | 先判断「现场修」还是「回退」，默认回退 | 半小时内 |
| **P2 · 不回滚，增量修复** | 单条文案错字；某个作品解说写错；非关键视觉微调 | **绝不回滚** —— 回滚会把别的东西一起退掉 | 正常排期 |
| **P3 · 不是事故** | 「网站打不开」但其实是**默认域名提示页**；双击本地 `checkup.html` 报 `Failed to fetch` | 不进本流程（见 §1.3） | —— |

### 1.2 「回滚 vs 现场修」的裁决规则（一句话）

> **如果「估计修好要花的时间」> 「回滚要花的时间」，就回滚。**

- **首次演练实测（2026-10-12）：静态托管回退总耗时 T2 − T0 = 2 分 35 秒**（主人视角 ≤ 2 分 11 秒）。
  其中「点上传」本身只占十几秒，**大头是 CDN 缓存刷新 + 确认生效**（约 1–2 分钟）。详见 `Day26-回滚演练记录.md`。
- 经验值：单文件覆盖上传 ≈ 1–3 分钟（含 CDN 生效），复杂热修复常在半小时以上。
- **安全优先原则**：拿不准就回滚。回滚是**可逆**的（大不了再传回新版）；线上带病运行**不可逆**（访客已经看到了）。

### 1.3 先排除「假事故」（这两条最容易误判）

| 现象 | 真相 | 处置 |
|---|---|---|
| 真实浏览器打开默认域名 → 404 + 一张「风险提醒」页 | **不是挂站**，是默认域名按 `Referer` 拦截「站外直接导航」 | 点「确定访问」即可进；见 §6.2 |
| 本机双击 `checkup.html` → 全面板 `Failed to fetch` | `file://` 的 `Origin` 是 `null`，不在 CORS 白名单 | **不是 bug**，用 http 打开或直接看线上页 |

## 三、第 3 层 · 代码回退（静态托管）—— **今日已实操**

### 3.1 前置：确认线上 = 本地

```bash
# 线上 index.html 的字节数（带站内 Referer，避开默认域名提示页）
curl -s -o _ref/verify/out/online.html -w "%{http_code} %{size_download}\n" \
  -H "Referer: https://art-exhibition-d7ggtul83d566a6c9-1499147979.tcloudbaseapp.com/" \
  "https://art-exhibition-d7ggtul83d566a6c9-1499147979.tcloudbaseapp.com/"

# 本地文件字节数
node -e "console.log(require('fs').statSync('mvp/index.html').size)"
```

**判据**：两个数字相等 → 线上 = 本地，可以动手。
（参考基线：v1.0 的 `mvp/index.html` = **142760 字节**。）

### 3.2 分步操作

| 步 | 谁做 | 动作 | 预期 |
|---|---|---|---|
| 1 | 我 | 取回「上一版」文件（**优先线上下载；不用 `git show`**，理由见 §0 铁律 2 的陷阱），放进独立目录并**以 `index.html` 命名** | 得到 `_ref/rollback/v1.0/index.html`，**142760 B / sha256 `2a165ed3…`**（自校验） |
| 2 | **主人** | 控制台 → 静态网站托管 → **文件管理** → 「上传文件」 → 选中上一版 **`index.html`**（同名文件自动覆盖） | 提示上传成功 |
| 3 | 主人 | 报出上传完成时刻 | 记为 **T1**，入演练记录 |
| 4 | **主人** | 浏览器硬刷新（`Ctrl+Shift+R`）打开首页 | 页面恢复正常 |
| 5 | 我 | 带站内 Referer 复核（§6.1）+ 记录 **T2** | HTTP 200 / 字节数 = 142760 / 无坏版本标记 |

> ⚠️ **缓存**：通过控制台上传文件**会自动刷新 CDN 节点缓存**。「缓存规则」的**变更**才是 1–3 分钟生效 ——
> 两者不要混。若页面仍是旧内容，先硬刷新，再等 1 分钟重试，**不要重复上传**。

> ⚠️ **文件名陷阱（实操必看）**：控制台的「上传文件」是**按文件名落位**的 ——
> 只有选中一个**本身就叫 `index.html`** 的文件，才会覆盖线上根文件 `/index.html`。
> 若你上传的是 `v1.0-index.html`，它只会**新增一个** `/v1.0-index.html`，线上首页**纹丝不动**。
> → 所以准备回退文件时，**务必放进独立目录、以 `index.html` 命名**（本次即 `_ref/rollback/v1.0/index.html`）。

### 3.3 多个文件都改了怎么办

- 只改 1 个文件 → 只覆盖那 1 个（**本次演练即此情形**）。
- 改了一整批 → 用「上传文件夹」整包覆盖（**注意本机 196.6MB 图片，上传会很慢**；这正是回滚耗时的主要来源）。
- **不要**为了省事删掉整个目录再重传 —— 删除期间网站是空的，等于把事故放大。

### 5.3 恢复步骤（有备份之后）

| 步 | 动作 | 注意 |
|---|---|---|
| 1 | **冻结写入** —— 暂不对外宣传，减少新数据产生 | 恢复期间的新写入会被覆盖 |

| 3 | 用 `db/schema.sql` 的**结构定义**确认表结构未被改坏 | ★ **只取结构，绝不整段执行该文件 —— 它会 DROP 表** |
| 4 | 用增量 SQL / `INSERT` 把备份数据插回 | **不做全表 DROP+重建**（除非确认可以全清） |
| 5 | 复核 | 见 §6.3 + §6.4 |

> 🚨 **绝对不能做的事**：直接重跑 `db/schema.sql` 或 `db/seed.sql`。
> 这两个脚本**开头就 DROP 表**，在线上执行 = 把「误删几条」升级成「全表清空」。设计上它们是**开发期脚本**。
